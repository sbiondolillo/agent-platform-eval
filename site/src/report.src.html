Agent platform eval

This report is a controls comparison of three ways to run a Claude agent on an issue: two of them run Claude Code, and the third runs the Managed Agents harness. The experiment ran to settle the direction of dotnet-software-factory v2.

Source: the repo. Design and status: the plan.

How to read it

Cloud Sessions is a VM that Anthropic manages. The platform is the factory at v1.1.0 in Docker, on a self-hosted runner in a lab VM. Both arms ran the same agent on the same model, claude-sonnet-5-5. They ran against one target repo, sbiondolillo/platform-eval-sample. Issue #1 is the delivery, and issue #2 is the probes.

A probe run in the real product proves every Cloud cell. A public asset proves every platform cell. Each cell links its proof.

The platform arm is a homelab: one runner host, a Squid proxy, a self-hosted vault and a self-hosted gateway. It stands in for an enterprise platform and is not one. The product fixes the Cloud cells. The platform cells are a floor. Where an enterprise component would change a row, the platform cell carries a footnote. The footnote says what changes.

The third arm, Managed Agents, was added on 2026-10-27. The Managed Agents docs prove its cells. Where the docs are silent, one session proves the cell. Managed Agents is the vendor's product. So, like the Cloud cells, the product fixes its cells.

The conditional

A verdict hides the rows that are the same under either choice. Read the conditional cell by cell.

Rows Cloud Sessions covers today

  • cloud-logging: the server-side transcript keeps the error text for signed-in accounts.
  • substrate: each session runs in its own Firecracker microVM.
  • vault-secret: the managed proxy attaches the secret on the way out, so the VM never holds a value it can read.
  • egress: a local relay tunnels HTTPS only to exact allowed hostnames. The platform covers this row too, with a hand-edited allowlist.
  • audit-record: the server-side transcript outside the VM is a record that a compromised agent cannot erase.
  • github-start: a label can start a Cloud session, through a glue job that the repo owner writes.
  • crash-resume: an idle reclaim keeps the disk and the history, so a session resumes on its own files.
  • toolchain: a setup script installs the SDK once, and later sessions start from a filesystem snapshot.

Rows the factory owner must build under either choice

Both arms act under the operator's admin account. So a non-admin identity and a protection with no bypass are build items, whichever arm wins.

  • forge-credential: the Cloud proxy injects the operator's own admin credential, and the platform's PAT is on the same admin account.
  • branch-protection: the Cloud session pushed to protected main as an admin bypass, and the protection would not stop a direct push from the platform's PAT.

Rows only the platform can hold

  • model-credential: on Cloud Sessions the agent can read the account's OAuth token. The platform container holds only a gateway key, and the platform owes a budget on that key.
  • tool-model-policy: on Cloud Sessions the operator picks any of twelve models with no control. The platform fixes the model in code, and owes a model list on the gateway key.

Rows the docs do not settle, with the probe result

  • run-history: no documented API or CLI command lists Cloud sessions or exports a transcript.
  • spend-attribution: Cloud lands the cost metric keyed by ccr.session.id once the collector host is on the environment's Allowed domains. Four earlier sessions exported nothing with the host only on a network secret. The platform lands it with a nine-name pass-through.
  • subagent-record: whether the subagent's own transcript outlives the container is pending the reclaim step.

setup-cost: Cloud Sessions took 25 operator steps and 4 secrets. The platform took 28 steps and no new secret, on top of 9 lab items and 4 secrets that the lab already held.

What the third arm changes

Managed Agents fills the same rows. It moves some rows into the product and leaves others with the owner.

Rows Managed Agents covers today

  • cloud-logging: the stderr of a failed command is in the session's events, read by API.
  • substrate: the agent runs as root in a Docker container inside a Firecracker microVM.
  • model-credential: the sandbox holds no model key, because the service makes the call. A commit-signing token is present, and its reach is not probed.
  • forge-credential: a credential helper injects the caller's token per request. So a read-only token gives fetch and a 403 on push.
  • egress: an unlisted hostname does not resolve. But api.anthropic.com answers from any sandbox.
  • run-history: the list and events endpoints export every session and its whole transcript.
  • spend-attribution: the API gives each session's list_cost with its metadata. A Console telemetry destination landed a session trace in Grafana Cloud.
  • audit-record: the events live outside the sandbox, read by a key the sandbox does not hold. The safeguard refused the in-sandbox route.
  • crash-resume: an idle sandbox is checkpointed. A later message resumes it with the files kept and the processes gone.
  • github-start: a workflow job starts a session with a workspace API key. The product has no idempotency key.
  • subagent-record: there is no subagent. Each reviewer is its own session with its own record.

Rows the owner must build on Managed Agents

  • tool-model-policy: the agent's model pin is a default that any create body overrides. So the control is whoever holds the API key.
  • branch-protection: require the judge check run. The session's token cannot push.
  • vault-secret: the docs are the only proof. The model-side safeguard refused the one-request test twice.
  • toolchain: the apt SDK is 10.0.113, and the target's band is 10.0.4xx. So the mutation angle stays on the runner.

setup-cost: Managed Agents took 6 operator steps and 2 new secrets. Cloud Sessions took 25 steps and 4 secrets. The platform took 28 steps and no new secret, on 9 lab items.

One rung per arm

A trust ladder grades the phases of one change: issue, plan, build, review, feedback, deliver and merge. Each rung up hands one phase from a person to an agent or to code.

  • Rung 0: every phase is a person.
  • Rung 1: plan and build are an agent. Review is an agent plus a person. Deliver is code.
  • Rung 2: feedback is an agent that answers its own review threads.
  • Rung 3: the issue is an agent.
  • Rung 4: the review loses its person.
  • Rung 5: merge is code.

Two lines hold at every rung. Deliver is code. The agent never holds the credential that opens the pull request.

Platform: rung 2

The factory's source pushes the branch and opens the pull request. The agent's container holds no forge credential. The review is an agent gate, with a person at the merge.

Proof: forge-credential, platform-delivery.

Cloud Sessions: below rung 1

The agent itself pushed the branch and opened PR 5. It did this through the managed proxy, with the operator's admin credential. In the branch-protection probe, it pushed to protected main. Deliver is the agent, not code.

Rung 1 needs a deliver step outside the session and a non-admin identity. The glue job from the github-start row is the place to build it.

Proof: forge-credential, branch-protection, github-start.

Managed Agents: rung 1, both lines held by the product

A Claude Code session built the subject. Two Managed Agents sessions reviewed it, with a person at the merge. Deliver is code. The workflow job posts the review and the check run with its own scoped token. The agent never holds the credential that opens or merges a pull request. The session's token is read-only, and the product's helper injects it.

Proof: forge-credential, branch-protection, platform-delivery.
